Introducción

Este informe documenta la validación de los cambios de seguridad, autenticación y control de acceso del Sistema PIAR, versión de referencia 1.1. Reúne la evidencia técnica comunicada desde la terminal integrada de VS Code y los chequeos repetidos en el proceso de auditoría, diferenciando su procedencia y alcance.

Resultado general. La integración reportada desde VS Code registró 8 pruebas aprobadas, 0 fallidas y 1 omitida en aproximadamente 4,93 segundos. La omisión corresponde a la prueba HTTP del rol Estudiante, que no está representado por el ENUM vigente. En la ejecución del proceso de auditoría, la suite unitaria explícita aprobó 8 pruebas; el comodín node --test tests/*.test.js aprobó 8 y detuvo la integración en preflight por falta de DB_HOST, antes de conectarse a MySQL. Por tanto, la seguridad no se considera completamente validada: hay pruebas y decisiones de permisos pendientes.

1. Objetivos

Objetivo general

Documentar la validación de las modificaciones de seguridad del Sistema PIAR con base en los resultados de auditoría disponibles, indicando el alcance comprobado, las limitaciones y las acciones necesarias para completar la verificación.

Objetivos específicos

  • Consolidar los chequeos estáticos, unitarios y de integración reportados.
  • Describir la matriz implementada de permisos por rol y recurso.
  • Distinguir resultados aprobados, ejecución detenida por entorno y pruebas omitidas.
  • Registrar hallazgos, asuntos institucionales pendientes y recomendaciones de cierre.

3. Alcance y metodología

La validación cubre revisión estática de controles y documentos, chequeo de sintaxis, pruebas unitarias, una integración HTTP/SQL reportada desde VS Code y controles de higiene del diff. Los documentos técnicos consultados fueron el informe de auditoría local, la matriz de permisos y el registro de resultados y pendientes de docs/auditoria-local/.

La integración local reportada se distingue de la ejecución actual: esta última no recibió DB_HOST, por lo que el preflight terminó antes de abrir conexión MySQL o escribir datos. La falta de configuración es una limitación del entorno de ejecución, no un fallo funcional demostrado del sistema. Los resultados de VS Code se presentan como informados, no como repetidos en esta auditoría.

La evidencia disponible no incluye capturas de pantalla ni salida TAP completa. No se afirma inspección posterior de piar_test; aunque el arnés documentado limpia los IDs sintéticos capturados en su bloque finally, no se confirmó directamente el estado final de esa base.

6.2 Ejecución detenida por condición del entorno

node --test tests/*.test.js registró 8 pruebas aprobadas y 1 fallida al detenerse el test de integración en el preflight por ausencia de DB_HOST. No alcanzó MySQL ni realizó escrituras. Se clasifica como ejecución bloqueada por configuración del entorno; no demuestra una falla funcional de PIAR.

6.3 Pruebas omitidas

El escenario HTTP de Estudiante fue omitido porque el ENUM usuario.rol no contempla ese valor. La migración de referencia contempla Docente, Psicóloga, Coordinador, Administrador y Rector. La omisión permanece visible y no se cuenta entre las aprobadas; existe cobertura unitaria de la denegación institucional reportada.

Revalidación local del 4 de octubre de 2026: se repitió la suite unitaria explícita y pasó 8/8 (610.497 ms). node --check pasó para los archivos backend, cliente y pruebas; git diff --check pasó con avisos LF/CRLF. Las variables DB requeridas estaban ausentes y los puertos 3307/8081 no tenían listener; por seguridad no se inició la integración ni se conectó a MySQL. Esta ejecución no verificó la limpieza de fixtures. Véanse los comandos y límites en docs/auditoria-local/evidencias-pruebas-20261004.txt.

8. Hallazgos y aspectos pendientes

  1. Prueba HTTP de Estudiante omitida. El esquema ENUM de la migración no admite el rol. Definir, con responsables institucionales, si se modifica el esquema o se mantiene cobertura alternativa. No alterar el ENUM como parte de esta evidencia.
  2. Permiso Docente sobre contenido PIAR. La matriz implementada deniega creación y actualización. Resolver la discrepancia funcional y documentar la decisión antes de modificar autorización.
  3. Entorno para repetición de integración. El proceso actual carecía de DB_HOST; repetir con configuración de prueba controlada y adjuntar la salida TAP completa sin exponer secretos.
  4. Estado de limpieza de datos. Verificar directamente los registros sintéticos posteriores en piar_test. El uso de finally por sí solo no certifica el estado residual real.
  5. Alcance de la evidencia. La integración aprobada procede de un resultado comunicado desde VS Code; no pudo repetirse en el proceso actual.
  6. Estado de control de versiones. Se reportaron cambios locales y documentos de auditoría sin confirmar. No se realizó commit, push ni despliegue.

10. Conclusiones y recomendaciones

La evidencia disponible respalda que se ejecutaron pruebas unitarias y que desde VS Code se reportó una integración con ocho aprobaciones y una omisión. También respalda chequeos de sintaxis y de diff aprobados, así como la corrección basada en changedRows para clasificar un UPDATE que no cambia filas. El resultado es favorable para los escenarios cubiertos, pero no permite declarar la seguridad completamente validada.

  1. Resolver institucionalmente el permiso de Docente para crear o actualizar PIAR y actualizar requisitos/matriz de manera coherente.
  2. Definir el tratamiento del rol Estudiante respecto del esquema y completar una validación dinámica compatible con la decisión aprobada.
  3. Repetir la integración en un entorno aislado configurado, guardar la salida TAP íntegra y revisar errores de preflight y limpieza sin divulgar credenciales.
  4. Verificar directamente el estado de los IDs sintéticos en piar_test y registrar el resultado antes de cerrar la evidencia.
  5. Conservar la distinción entre pruebas aprobadas, omitidas y no ejecutadas; adjuntar evidencias originales disponibles en anexos cuando se entreguen.
